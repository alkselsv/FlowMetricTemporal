# FlowMetric Temporal

`FlowMetric Temporal` — отдельный обучаемый модуль для классификации коротких
эпизодов взаимодействия сотрудника, клиента и стола. Он дополняет основной
FlowMetric: основной проект находит людей, назначает им роли и строит
траектории, а этот проект анализирует динамику уже сформированного эпизода.

Модель относит каждый эпизод к одному из четырёх классов:

| Класс | Смысл |
|---|---|
| `service` | сотрудник действительно обслуживает выбранного клиента |
| `passing` | сотрудник проходит рядом, не начиная обслуживание |
| `waiting` | сотрудник или клиент остаётся рядом без обслуживания |
| `cleanup` | сотрудник убирает или подготавливает стол |

Это специализированная модель анализа видео и траекторий, а не
визуально-языковая модель (VLM). При промышленной эксплуатации она не отправляет
изображения во внешний программный интерфейс (API) и не использует текстовые
запросы. VLM можно подключить отдельно для предварительной разметки, поиска
сложных отрицательных примеров или в качестве модели-учителя.

## Зачем нужен отдельный временной классификатор

Один кадр часто не позволяет отличить обслуживание от похожих ситуаций:

- сотрудник просто стоит рядом со столом;
- проходит между столами;
- обслуживает соседнего клиента;
- разговаривает с коллегой;
- остаётся рядом после завершения обслуживания;
- забирает посуду без взаимодействия с клиентом.

Различие проявляется во времени: меняются расстояния, скорости, положение людей
относительно стола и содержимое областей интереса (ROI). Поэтому модель
одновременно получает изображения и геометрию траекторий на последовательности
кадров.

## Текущее состояние

Реализована первая полностью работоспособная базовая версия:

1. импорт ручной JSONL-разметки или её автоматическое формирование из текущего
   контрольного набора FlowMetric;
2. синхронное извлечение областей интереса `staff`, `customer` и `table`;
3. построение 20 траекторных признаков;
4. обучение свёрточной нейронной сети и временного трансформера;
5. выбор контрольной точки по макро-F1 на проверочной выборке;
6. пакетное получение предсказаний с вероятностями всех классов;
7. строгая проверка схемы набора данных и версии контрольной точки;
8. команда сквозной обработки текущего видео FlowMetric.

Базовая версия предназначена для проверки полного контура и начала сбора данных.
Она пока не является готовой промышленной моделью: текущий контрольный набор
содержит только один короткий ролик и две наблюдаемые эталонные пары обслуживания.

## Архитектура решения

```text
                  FlowMetric tracks.json
                           +
                   размеченный интервал
                           │
          ┌────────────────┼─────────────────┐
          │                │                 │
 область staff     область customer     область table
          │                │                 │
          └──── общая свёрточная сеть ───────┘
                           │
              три визуальных представления
                           │
tracks ──► 20 траекторных признаков ──► траекторный многослойный перцептрон
                           │
                   объединение признаков
                           │
             обучаемые позиционные векторы
                           │
             кодировщик временного трансформера
                           │
              временное объединение по маске
                           │
              service / passing / waiting / cleanup
```

Визуальный кодировщик общий для всех трёх потоков. Это уменьшает число параметров
и заставляет модель использовать сопоставимое пространство признаков для людей
и стола. Каждый временной шаг содержит:

```text
staff_embedding + customer_embedding + table_embedding + trajectory_embedding
```

Конфигурация по умолчанию:

| Параметр | Значение |
|---|---:|
| размер одного визуального представления | 96 |
| размер траекторного представления | 32 |
| общий размер скрытого слоя | 320 |
| число голов внимания | 8 |
| число слоёв трансформера | 3 |
| коэффициент исключения | 0.15 |
| максимальное число кадров | 64 |
| число классов | 4 |

Условие конфигурации: `hidden_dim = 3 × visual_dim + trajectory_dim`, а
`hidden_dim` должен делиться на число голов внимания.

## Связь с основным FlowMetric

FlowMetric Temporal не запускает модули обнаружения и сопровождения самостоятельно.
Он ожидает:

- исходное видео;
- `tracks.json`, созданный FlowMetric;
- идентификаторы сотрудника и клиента;
- границы эпизода в кадрах;
- необязательный `table_box`.

Ответственность модулей разделена так:

| FlowMetric | FlowMetric Temporal |
|---|---|
| обнаружение людей | классификация готового эпизода |
| сопровождение и повторная идентификация | временное моделирование взаимодействия |
| назначение ролей | различение обслуживания и сложных отрицательных примеров |
| генерация кандидатов | вероятность каждого класса |
| карта столов | использование области интереса стола и геометрии |

Временная модель не должна создавать новые идентификаторы или изменять границы
кандидата. В будущей интеграции она станет модулем проверки основного FlowMetric.

- Python 3.10 или новее;
- NumPy;
- OpenCV без графического интерфейса;
- SciPy;
- PyTorch 2.2 или новее.

```bash
cd /Users/alkselsv/Projects/FlowMetricTemporal

python3 -m venv .venv
source .venv/bin/activate
pip install -e '.[dev]'

python -m unittest discover -s tests -v

```

`--device auto` выбирает CUDA, затем Apple MPS, затем CPU. Можно потребовать
конкретное устройство через `--device cpu`, `--device mps`, `--device cuda` или
`--device cuda:N`. Если явно указанное устройство недоступно, команда завершится
ошибкой вместо незаметного перехода на CPU.

## Быстрый сквозной запуск на текущих данных

Текущий репозиторий FlowMetric уже содержит исходное видео, эталонную разметку,
`tracks.json` и карту столов. Полный демонстрационный прогон запускается одной
командой:

```bash
cd /Users/alkselsv/Projects/FlowMetricTemporal

flowmetric-temporal current-data \
  --flowmetric-root /Users/alkselsv/Projects/FlowMetric \
  --out runs/current-data \
  --device auto \
  --epochs 30
```

Команда последовательно выполняет:

```text
сопоставление опорных точек
    → начальная разметка
    → извлечение областей интереса и траекторных признаков
    → обучение
    → лучшая контрольная точка
    → предсказания на проверочной выборке
```

Результат:

```text
runs/current-data/
  annotations.jsonl
  episodes/
    manifest.jsonl
    gt_service_*.npz
    weak_passing_*.npz
    weak_waiting_*.npz
    weak_cleanup_*.npz
  best.pt
  val_predictions.jsonl
  run.json
```

Назначение файлов:

| Файл | Содержимое |
|---|---|
| `annotations.jsonl` | эталонные и слабо размеченные эпизоды с указанием источника |
| `episodes/*.npz` | изображения областей интереса, траектории, маска и номера кадров |
| `episodes/manifest.jsonl` | реестр извлечённых эпизодов для `Dataset` и `DataLoader` |
| `best.pt` | контрольная точка лучшей эпохи по макро-F1 на проверочной выборке |
| `val_predictions.jsonl` | вероятности классов для проверочной выборки |
| `run.json` | пути, количество эпизодов и итоговые метрики запуска |

Для быстрой проверки контура можно уменьшить объём вычислений:

```bash
flowmetric-temporal current-data \
  --flowmetric-root /Users/alkselsv/Projects/FlowMetric \
  --out runs/smoke \
  --frames 4 \
  --crop-size 32 \
  --epochs 1 \
  --batch-size 4 \
  --device cpu
```

Такой запуск проверяет код, но его контрольную точку не следует использовать как
обученную модель.

## Как работает автоматическая начальная разметка

Команда `bootstrap-current` создаёт проверяемую стартовую разметку:

```bash
flowmetric-temporal bootstrap-current \
  --flowmetric-root /Users/alkselsv/Projects/FlowMetric \
  --out runs/current-data/annotations.jsonl
```

По умолчанию используются:

```text
benchmark/ground_truth.json
config/tables.json
data/hf_*.mp4
data/output/service_verifier_tables_run/tracks.json
```

Другой результат сопровождения можно передать путём относительно корня FlowMetric:

```bash
flowmetric-temporal bootstrap-current \
  --flowmetric-root /Users/alkselsv/Projects/FlowMetric \
  --tracks data/output/local/tracks.json \
  --out runs/local-tracks/annotations.jsonl
```

Автоматическое формирование начальной разметки состоит из следующих этапов.

### 1. Сопоставление идентификаторов эталонной разметки и треков

Эталонная разметка содержит точки головы на опорных кадрах, а `tracks.json` —
ограничивающие прямоугольники с идентификаторами трекера. Сопоставление повторяет
логику контрольного набора FlowMetric:

- оставляет ограничивающие прямоугольники, содержащие точку головы с небольшим
  допуском;
- штрафует короткие фрагменты траекторий;
- исключает вложенные короткие ограничивающие прямоугольники;
- решает задачу глобального назначения венгерским алгоритмом;
- запрещает повторное использование одного идентификатора трека.

### 2. Положительные эпизоды

`service_start` и `service_end` объединяются по паре `staff/customer`.
Интервалы переводятся из секунд в номера кадров. Нулевой левосторонне
цензурированный эпизод, заканчивающийся на кадре 0, пропускается, поскольку в
видео нет наблюдаемой динамики обслуживания.

На текущем контрольном наборе получаются две положительные пары `service`.

### 3. Слабо размеченные сложные отрицательные примеры

Для пар сотрудник–клиент строятся скользящие окна и вычисляются:

- среднее и минимальное расстояние между людьми в высотах тела;
- скорость движения сотрудника;
- доля кадров, в которых сотрудник находится около выбранного стола.

По этим признакам упорядочиваются кандидаты `passing`, `waiting` и `cleanup`.
По умолчанию выбирается до шести кандидатов каждого класса.

Каждая такая строка содержит:

```json
{
  "label_source": "weak_geometry_heuristic",
  "review_required": true,
  "weak_label_scores": {
    "passing": 1.42,
    "waiting": 0.71,
    "cleanup": 1.08
  },
  "window_stats": {
    "mean_distance": 1.28,
    "min_distance": 0.14,
    "staff_speed": 1.78,
    "near_table_ratio": 0.5
  }
}
```

Важно: слабые метки — это очередь кандидатов для ручной проверки, а не эталонная
разметка. Особенно ненадёжен класс `cleanup`: геометрия показывает присутствие
сотрудника возле стола и удалённость выбранного клиента, но не доказывает факт
уборки. До ручной проверки эти примеры годятся только для проверки конвейера и
экспериментов с обучением на слабо размеченных данных.

### 4. Ограничение демонстрационной проверки

Текущий ролик длится примерно 15 секунд. Автоматическая разметка вынуждена
формировать `train` и `val` из одного видео. Такие выборки визуально и временно
зависимы, поэтому полученный макро-F1 на проверочной выборке не измеряет
обобщающую способность модели. Для настоящей оценки данные необходимо разделять
по исходным видео, камерам или заведениям.

## Подготовка собственного набора данных

Для промышленных экспериментов рекомендуется создавать JSONL вручную или через
отдельный интерфейс разметки. Одна строка описывает одну пару и один интервал:

```json
{
  "episode_id": "venue01_clip001_000120_000240",
  "label": "service",
  "split": "train",
  "video": "/data/venue01/clip001.mp4",
  "tracks": "/data/venue01/tracks.json",
  "start_frame": 120,
  "end_frame": 240,
  "staff_id": "7",
  "customer_id": "12",
  "table_box": [410, 280, 790, 610]
}
```

Поля:

| Поле | Обязательное | Описание |
|---|---|---|
| `episode_id` | да | уникальный пригодный для имени файла идентификатор без `/` и `\\` |
| `label` | да | `service`, `passing`, `waiting` или `cleanup` |
| `split` | нет | `train` по умолчанию; для обучения нужен также `val` |
| `video` | да | путь к исходному видео |
| `tracks` | да | путь к совместимому `tracks.json` |
| `start_frame` | да | первый кадр интервала, включительно |
| `end_frame` | да | последний кадр интервала, включительно |
| `staff_id` | да | идентификатор сотрудника внутри `tracks.json` |
| `customer_id` | да | идентификатор клиента внутри `tracks.json` |
| `table_box` | нет | `[x1, y1, x2, y2]`; без него изображения стола заполняются нулями |

Дополнительные поля разрешены в аннотациях и могут использоваться для проверки
происхождения данных, но модуль извлечения переносит в реестр только `episode_id`,
`label`, `split` и путь к `.npz`. Поэтому исходный `annotations.jsonl` следует
сохранять вместе с набором данных.

Пути разрешаются относительно текущего рабочего каталога процесса, а не
автоматически относительно расположения файла аннотаций. Для воспроизводимых
запусков удобнее использовать абсолютные пути или запускать команды из одного
и того же каталога.

## Требования к `tracks.json`

Ожидается стандартный результат FlowMetric:

```json
{
  "fps": 24.0,
  "width": 1920,
  "height": 1080,
  "n_frames": 361,
  "tracks": {
    "7": {
      "role": "staff",
      "frames": [120, 121, 122],
      "boxes": [
        [100.0, 200.0, 220.0, 520.0],
        [102.0, 201.0, 222.0, 521.0],
        [105.0, 202.0, 225.0, 522.0]
      ]
    }
  }
}
```

Для каждого идентификатора массивы `frames` и `boxes` должны иметь одинаковую
длину, кадры должны быть строго возрастающими, а координаты — конечными числами.
Модуль извлечения линейно интерполирует ограничивающие прямоугольники на выбранные
временные точки и помечает точку невидимой, если ближайшее наблюдение дальше
половины секунды.

## Извлечение тензоров эпизода

```bash
flowmetric-temporal extract \
  --annotations annotations.jsonl \
  --out data/episodes \
  --frames 16 \
  --crop-size 112
```

Из каждого интервала равномерно выбирается фиксированное количество кадров.
Для каждого временного шага:

1. интерполируются ограничивающие прямоугольники сотрудника и клиента;
2. прямоугольники расширяются на 15% и ограничиваются границами кадра;
3. изображения областей интереса преобразуются из цветового пространства BGR
   в RGB;
4. изображение каждой области интереса масштабируется до размера
   `crop-size × crop-size`;
5. строятся траекторные признаки;
6. создаётся логическая маска совместной видимости.

Если `table_box` отсутствует, массив изображения стола заполняется нулями. Если
человек не считается видимым на выбранном шаге, соответствующий массив
изображения также заполняется нулями, а временной шаг исключается маской при
временном объединении и вычислении внимания.

Каждый `.npz` содержит:

| Массив | Тип | Форма | Смысл |
|---|---|---|---|
| `staff` | `uint8` | `[T,H,W,3]` | изображения сотрудника в цветовом пространстве RGB |
| `customer` | `uint8` | `[T,H,W,3]` | изображения клиента в цветовом пространстве RGB |
| `table` | `uint8` | `[T,H,W,3]` | изображения стола в цветовом пространстве RGB |
| `trajectory` | `float32` | `[T,20]` | траекторные признаки |
| `mask` | `bool` | `[T]` | совместная видимость людей |
| `frames` | целые числа | `[T]` | номера выбранных кадров |

При загрузке изображения преобразуются в `[T,3,H,W]`, `float32` и диапазон
`[0,1]`. Набор данных отклоняет несовместимые типы, формы и эпизоды без единого
допустимого временного шага.

## Траекторные признаки

Координаты и размеры нормализуются на ширину и высоту кадра.

| Индексы | Признаки |
|---|---|
| 0–3 | `staff_cx`, `staff_cy`, `staff_w`, `staff_h` |
| 4–7 | `customer_cx`, `customer_cy`, `customer_w`, `customer_h` |
| 8–11 | `table_cx`, `table_cy`, `table_w`, `table_h` |
| 12–13 | направление от сотрудника к клиенту: `dx`, `dy` |
| 14 | евклидово расстояние сотрудник–клиент |
| 15–16 | скорость центра сотрудника: `vx`, `vy` |
| 17–18 | скорость центра клиента: `vx`, `vy` |
| 19 | `joint_visible` |

Скорости вычисляются между выбранными временными точками в нормализованных
координатах за секунду. Если стол не задан, его четыре признака равны нулю.

## Обучение

```bash
flowmetric-temporal train \
  --manifest data/episodes/manifest.jsonl \
  --out checkpoints/best.pt \
  --epochs 30 \
  --batch-size 16 \
  --learning-rate 3e-4 \
  --weight-decay 1e-4 \
  --device auto \
  --workers 0 \
  --seed 17
```

Текущий цикл обучения использует:

- веса классов, обратно пропорциональные их частоте;
- `CrossEntropyLoss`;
- `AdamW`;
- косинусное расписание скорости обучения;
- ограничение нормы градиента значением 1.0;
- лучшую контрольную точку по макро-F1 на проверочной выборке;
- фиксированные начальные значения генераторов случайных чисел Python, NumPy и PyTorch.

После каждой эпохи печатается JSON:

```json
{"epoch": 3, "accuracy": 0.75, "macro_f1": 0.68, "train_loss": 0.91}
```

Макро-F1 вычисляется по всем четырём классам. Если класс отсутствует в
проверочной выборке, его F1 равен нулю; это помогает обнаруживать неполную
проверочную выборку, но делает итоговую метрику низкой.

### Что хранится в контрольной точке

`best.pt` содержит:

- `format_version`;
- фиксированный порядок меток;
- фиксированный порядок траекторных признаков;
- конфигурацию модели;
- `state_dict`;
- номер лучшей эпохи;
- проверочные метрики лучшей эпохи.

Среда выполнения отказывается загружать контрольную точку с неизвестной версией, другим
порядком классов или несовместимым набором признаков. Это защищает от тихой
ошибки, когда новый код интерпретирует старые веса по другой схеме.

## Получение предсказаний

```bash
flowmetric-temporal predict \
  --manifest data/episodes/manifest.jsonl \
  --checkpoint checkpoints/best.pt \
  --out predictions.jsonl \
  --split val \
  --batch-size 16 \
  --device auto
```

Без `--split` обрабатываются все строки реестра. Формат результата:

```json
{
  "episode_id": "venue01_clip001_000120_000240",
  "label": "service",
  "confidence": 0.73,
  "probabilities": {
    "service": 0.73,
    "passing": 0.11,
    "waiting": 0.10,
    "cleanup": 0.06
  }
}
```

`confidence` — максимальная вероятность после функции softmax, а не
откалиброванная вероятность правильности. Для промышленного применения нужно
отдельно выполнить температурное масштабирование или другую калибровку и
определить порог отказа от предсказания (`abstain`).

## Рекомендации по разметке

### Правило выбора пары

Один эпизод всегда относится к конкретной паре `staff_id/customer_id`. Если
сотрудник обслуживает соседнего клиента, то для неправильной пары это сложный
отрицательный пример, а для правильной пары — `service`. Оба примера полезно сохранить.

### Сложные отрицательные примеры

| Сцена | Рекомендуемая метка |
|---|---|
| сотрудник проходит между столами | `passing` |
| сотрудник кратко пересекает область клиента | `passing` |
| сотрудник стоит рядом без взаимодействия | `waiting` |
| сотрудник остаётся после обслуживания | следующий эпизод `waiting` или `cleanup` по фактическому действию |
| уборка посуды или поверхности | `cleanup` |
| подготовка пустого стола | `cleanup` |
| обслуживание соседнего клиента | `waiting` для неправильной пары и `service` для правильной |

Разговор с коллегой без выбранного клиента не соответствует текущей спецификации
парного эпизода. Его следует отфильтровывать генератором кандидатов. Если такие
сцены должны классифицироваться моделью, нужно осознанно добавить класс `other`,
обновить версии схемы и формата контрольной точки, а затем переразметить набор данных.

### Границы эпизодов

- захватывайте небольшой контекст до и после действия;
- используйте одинаковое правило границ для всех классов;
- не объединяйте несколько разных действий в один интервал;
- длинное присутствие рядом лучше делить на однородные короткие эпизоды;
- отмечайте цензурированные границы отдельно в исходной системе разметки.

### Обучающая, проверочная и тестовая выборки

Нельзя случайно распределять соседние окна одного видео между выборками: они содержат
почти одинаковые кадры и создают сильную утечку. Предпочтительный порядок:

1. тестовая выборка (`test`) — полностью отдельные заведения или камеры;
2. проверочная выборка (`validation`) — отдельные исходные ролики;
3. обучающая выборка (`train`) — оставшиеся ролики;
4. соседние окна одного ролика всегда находятся в одной выборке.

Дополнительно следует контролировать баланс камер, освещения, плотности зала,
типов формы сотрудников, ракурсов столов и длительности эпизодов.

## Оценка качества

Основная метрика базовой версии при автономной оценке — макро-F1, поскольку
классы несбалансированы, а ошибки на редких сложных отрицательных примерах важны
не меньше общей доли правильных ответов.

Для реальной оценки рекомендуется считать:

- точность, полноту и F1 для каждого класса;
- матрицу ошибок;
- долю ложных срабатываний `service` на каждом типе сложных отрицательных примеров;
- полноту `service` по дальности, перекрытию и длительности;
- метрики отдельно по камерам и заведениям;
- ошибку калибровки и долю обработанных примеров при пороге отказа от предсказания;
- сквозные точность и полноту событий после интеграции с FlowMetric.

Нужно различать две оценки:

1. **только классификатор** — эпизод и правильные идентификаторы уже даны;
2. **сквозная оценка** — учитываются ошибки обнаружения, сопровождения, ролей и
   генератора кандидатов.

Высокая метрика отдельного классификатора не гарантирует качество всей системы.

## Известные ограничения

- визуальный кодировщик обучается с нуля, предварительно обученная основа пока
  отсутствует;
- нет искусственных преобразований изображений и видео для расширения данных;
- нет отдельного класса `other`;
- нет калибровки уверенности и режима отказа от предсказания;
- нет интерфейса для просмотра и исправления слабых меток;
- для всех временных шагов эпизода используется одна область интереса стола;
- автоматическая разметка использует геометрию, но не подтверждает фактическую
  уборку;
- текущая выборка слишком мала для измерения обобщения;
- основной FlowMetric пока не использует контрольную точку через `ServiceVerifier`;
- модель классифицирует предложенный эпизод, но не локализует его границы.

## Типичные проблемы

### В реестре нет строк для проверочной выборки

В аннотациях отсутствуют строки `"split": "val"`. Добавьте независимую
проверочную выборку; не копируйте туда те же эпизоды из обучающей выборки.

### Маска не выбирает ни одного временного шага

В выбранном интервале сотрудник и клиент не наблюдаются одновременно. Проверьте
идентификаторы, границы эпизода и качество сопровождения.

### Несовместимые метки контрольной точки

Контрольная точка создана с другой схемой классов. Используйте совместимую версию
кода или переобучите модель после изменения схемы.

### Запрошенное устройство недоступно

Используйте `--device auto` или установите PyTorch со сборкой для нужного
ускорителя. Явный `mps`/`cuda` специально не переключается на CPU автоматически.

### Очень высокая проверочная метрика на одном видео

Скорее всего, соседние временные окна попали одновременно в обучающую и
проверочную выборки. Заново разделите данные по исходным видео или камерам.

## План развития

Ближайшие практические этапы:

1. интерфейс просмотра и ручной коррекции автоматически размеченных кандидатов;
2. сбор нескольких независимых видео и разделение выборок по камерам;
3. предварительно обученный визуальный кодировщик и искусственное расширение данных;
4. алгоритм выборки с балансом классов, камер и типов сложных отрицательных примеров;
5. температурное масштабирование и порог отказа от предсказания;
6. адаптер контрольной точки к интерфейсу `ServiceVerifier` основного FlowMetric;
7. сквозной контрольный набор с учётом полноты генератора кандидатов;
8. дистилляция знаний из видео- или визуально-языковой модели-учителя при
   наличии достаточной разметки.

Главный следующий шаг — не усложнение архитектуры, а получение проверенной
эпизодной разметки. На небольшом и зависимом наборе данных более крупная модель лишь
быстрее запомнит конкретную камеру и людей.
